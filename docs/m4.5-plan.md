# M4.5 plan: Full uninstall

Detailed plan for the [M4.5 roadmap items](roadmap.md#m45-full-uninstall).

**Status:** planned, 2026-11-20.

## What M4.5 delivers

- **One "remove everything" choice per platform.** It removes the service's state (imported config, settings, logs), the `nebula-gui` group, and **every user's** own nebula-gui files: saved peer names, masking names, the app log, app preferences and the start-at-sign-in entry. The uninstaller already runs as administrator, so it can reach every user's files, and this is the only way to leave no trace on a shared computer.
- **A normal uninstall stays a reinstall-friendly one.** Without the choice, the imported config and each user's files are kept, as today. The one change is that every uninstall now removes every user's start-at-sign-in entry on all three platforms, because it would point at an app that's gone. macOS already does this.
- **A Mac uninstall without Terminal:** an **Uninstall nebula-gui** app in Applications, and **Help → Uninstall nebula-gui…** in the app, which opens it.

## What's left behind today

| | Service state | Each user's files | Start-at-sign-in entry | Group, user |
|---|---|---|---|---|
| Linux | `/var/lib/nebula-gui` (kept even on purge) | `~/.config/nebula-gui/`, `~/.config/fyne/io.github.tucono.nebulagui/` (kept) | `~/.config/autostart/nebula-gui.desktop` (kept) | `nebula-gui`, `nebula-guid` (kept) |
| macOS | `/Library/Application Support/nebula-gui` (`--remove-settings` removes it) | `~/Library/Application Support/nebula-gui/`, `~/Library/Preferences/fyne/io.github.tucono.nebulagui/`, `~/Library/Caches/nebula-gui/` (kept) | `~/Library/LaunchAgents/io.github.tucono.nebulagui.plist` (removed) | `nebula-gui` (`--remove-settings` removes it) |
| Windows | `%ProgramData%\nebula-gui` (the "remove settings" question removes it) | `%AppData%\nebula-gui\`, `%AppData%\fyne\io.github.tucono.nebulagui\` (kept) | `nebula-gui` under `HKCU\…\Run` and `…\StartupApproved\Run` (kept) | `nebula-gui` (the question removes it) |

`nebula-gui/` holds `peers.json`, `mask-names.json` and `logs/`. The `fyne/<app ID>/` folder is where Fyne keeps `preferences.json`. The per-user instance socket lives in `$XDG_RUNTIME_DIR` on Linux, which is emptied at sign-out, and in the cache folder on macOS. Reports saved from **Get help…** go wherever the user chose, so they're the user's files, not the app's, and are never touched.

## One list of a user's files

The paths are spread over `peerstore.go`, `mask.go`, `applog.go`, `instance_unix.go`, `internal/autostart` and Fyne itself. A new package, `internal/userfiles` (no Fyne, so it builds for every OS from one machine), becomes the one place that names them:

```go
// For computes a user's nebula-gui files from their home folder, as the
// app would find them when that user runs it.
func For(goos, home string) Files

type Files struct {
	Dirs      []string // removed whole: nebula-gui/, fyne/<app ID>/, the macOS cache folder
	Autostart string   // the XDG file or LaunchAgent; empty on Windows (a registry value)
}
```

- The GUI's stores take their folder from it, so the app and the uninstaller can't drift apart.
- A test checks that `For(runtime.GOOS, home)` matches `os.UserConfigDir()` and Fyne's storage root for the user running the test. If a Fyne upgrade moves its preferences, this test fails.
- `XDG_CONFIG_HOME` set to somewhere other than `~/.config` can't be seen from outside the user's session; those files are missed and the plan says so in [platforms.md](platforms.md). Nobody on the network is known to set it.

## Removing every user's files: `nebula-guid remove-user-files`

A new hidden subcommand of the service binary, which every uninstaller already has on disk and runs as root or administrator:

```
nebula-guid remove-user-files [--autostart-only]
```

- **Finding users.** Linux: `getent passwd` entries with a UID of 1000 or more and a home folder that exists. macOS: `/Users/*` except `Shared`. Windows: the profiles under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList` whose SID starts `S-1-5-21-` (real accounts, not system ones).
- **Removing.** For each user, `For(goos, home)`. `--autostart-only` removes just the start-at-sign-in entry (a normal uninstall); without it, everything (remove everything).
- **Windows registry values.** For a user who is signed in, their hive is already loaded under `HKEY_USERS\<SID>`. For one who isn't, `NTUSER.DAT` is loaded under a temporary key (`RegLoadKey`, after enabling the backup and restore privileges), the two values are deleted, and it's unloaded again. A hive that can't be loaded (the profile is in use oddly, or damaged) is reported and skipped.
- **Safety.** It only ever deletes the fixed names above, inside a folder it got from the system's user list. It never follows a symlink out of the home folder: each path is checked with `Lstat`, and a symlinked `nebula-gui` folder is removed as a link, not followed. Each failure is printed and the rest carry on; the exit code says whether anything failed, and the uninstallers don't stop on it.
- **Tests:** on fake home folders in a temp directory, for every OS layout: everything removed, `--autostart-only` keeping the rest, another app's files next to ours untouched, a symlink not followed, a missing folder not an error. The user-listing parts get a small test each with fake input (a `passwd` file, a directory list); the Windows hive loading is checked by the smoke tests.

## Per platform

### Windows

The Inno Setup question widens and keeps its default of **No**:

> **Remove everything nebula-gui saved on this computer?**
>
> This deletes the imported config, the service's logs and the nebula-gui group, and every user's saved peer names, app log and settings. Choose No to keep them for a reinstall.

- `usUninstall`, before the files go: `nebula-guid remove-user-files`, with `--autostart-only` unless the answer was Yes. Then the existing steps.
- `/REMOVESETTINGS` keeps its name for silent uninstalls and gains the wider meaning.

### macOS

- **`uninstall.sh`** gains `--remove-everything`, with `--remove-settings` kept as another name for it. Before the libexec folder goes, it runs `nebula-guid remove-user-files` (with or without `--autostart-only`), replacing the LaunchAgent loop. It also removes the uninstaller app and forgets the package receipt.
- **Uninstall nebula-gui.app**: a small AppleScript app built by `build-pkg.sh` with `osacompile`, with the nebula-gui icon, installed to `/Applications`. It shows:

  > **Uninstall nebula-gui?**
  > This removes the app and its background service, which ends the Nebula connection.
  >
  > [Cancel] [Keep settings and uninstall] [Remove everything and uninstall]

  It then runs `uninstall.sh` through `do shell script … with administrator privileges`, so macOS asks for the password in its normal way, and ends with "nebula-gui has been removed." A failure shows the script's error text. If the main app won't open, this still works.
- **Help → Uninstall nebula-gui…** (macOS only) opens that app with `open -a`, and the GUI quits so it isn't in the way. If the uninstaller app is missing, the menu item isn't shown.
- The README's Terminal command stays, as the fallback.

### Linux

Package managers can't ask questions, so the choice is the command:

| Command | What it removes |
|---|---|
| `sudo apt remove nebula-gui`, `sudo dnf remove nebula-gui` | The app and service, and every user's start-at-sign-in entry. Config and users' files kept. |
| `sudo apt purge nebula-gui` | Everything, including `/var/lib/nebula-gui`, every user's files, and the `nebula-gui` group and `nebula-guid` user. |
| Fedora: `sudo nebula-guid remove-everything`, then `sudo dnf remove nebula-gui` | The same, since rpm has no purge. |

- **`preremove.sh`** on removal (not upgrade): quits the app in every session (`pkill -x nebula-gui`, as the other platforms do, so it can't write its preferences back after they're gone), then `nebula-guid remove-user-files --autostart-only`, then stops the service as today.
- **`postremove.sh` on `purge`** runs after the binaries are gone, so it can't call `nebula-guid`. It does the same removal in a few lines of shell: `/var/lib/nebula-gui`, then for each `getent passwd` user with UID ≥ 1000 the folders `For` names for Linux, then `groupdel`/`userdel`. A Go test reads `postremove.sh` and checks that it names every Linux path `For` returns, so the two can't drift.
- **`nebula-guid remove-everything`** (Linux only): the service state, all users' files, the group and user, with a confirmation prompt unless `--yes`. It refuses while the service is running and says to stop it first; on Fedora the README says to run it before `dnf remove`.

## Tests

- `internal/userfiles`: the path table per OS, and the match with `os.UserConfigDir()` and Fyne's root.
- `remove-user-files`: fake homes as above.
- `postremove.sh` names every Linux path.
- **CI on Linux:** the package job installs the `.deb`, creates two test users with files in the right places and an autostart entry, runs `apt remove` and checks that only the autostart entries went, then `apt purge` and checks that everything went. A `check-uninstall.sh` beside `check-install.sh` does the checking. The same for the `.rpm`, with `nebula-guid remove-everything`.
- **CI on macOS:** install the `.pkg`, create the files in a fake second home under `/Users`, run `uninstall.sh` (and `--remove-everything` on a second install), and check.
- **CI on Windows:** a silent install and uninstall (`/VERYSILENT`, then with `/REMOVESETTINGS`) with the files of the runner's own user, checked by `check-uninstall.ps1`. A second, signed-out user's hive can't easily be set up on a runner, so that's a smoke test.

## Smoke tests

1. **Windows VM, two users.** Both have used the app (peer names, start at sign-in on). Signed in as the admin, with the other user signed out: uninstall, answer **No**. Both users' Run entries are gone (Task Manager → Startup apps on each); their `%AppData%\nebula-gui` is still there. Reinstall, uninstall again, answer **Yes**: both users' folders and `%ProgramData%\nebula-gui` are gone, and `net localgroup nebula-gui` says the group doesn't exist.
2. **Mac.** Open **Uninstall nebula-gui** from Applications, choose **Keep settings and uninstall**, enter the password: the app, service and uninstaller are gone, and `~/Library/Application Support/nebula-gui` remains. Reinstall; this time use **Help → Uninstall nebula-gui…** and **Remove everything**: nothing from the "What's left behind" table remains, and `dscl . -read /Groups/nebula-gui` fails.
3. **Linux (Pop!_OS).** `apt remove`: the autostart file is gone, `~/.config/nebula-gui` kept. Reinstall, `apt purge`: nothing from the table remains, and `getent group nebula-gui` prints nothing.

## Risks and decisions

- **Deleting other people's files.** It's the point of the option, and it's only done when the admin chooses it, under a question that says "every user". The deletion is limited to fixed names in system-listed home folders, never a pattern or a path from a config.
- **A user's files on a network home or an unmounted encrypted home** (FileVault per user on old macOS, `ecryptfs` on Linux) can't be reached while that user is signed out. They're skipped silently; the README says so in a line.
- **Hive loading on Windows** is the one fiddly part. If it proves unreliable, the fallback is to remove only signed-in users' registry values and every user's folders, leaving a dead Startup entry for the others, which Windows shows as "not found" and the user can delete.
- **Linux purge in shell.** Duplicates the Linux paths once, guarded by the Go test above.
- **No ADR:** this adds to what the installers do (ADR-007, ADR-008) without changing a decision. [platforms.md](platforms.md)'s paragraph on what uninstalling leaves behind is rewritten.
